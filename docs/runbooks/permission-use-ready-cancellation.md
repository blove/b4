# Cancel a saved-permission run while Ready

`cancel_permission_use_ready` is the explicit embedded management operation for a genuinely authorized NewUse Ready2. It derives Kernel Cancelled3 without claiming an invocation, calling an effect or creating a callback receipt. The immutable Use and original saved approval/decision/consumed-grant evidence remain unchanged. Original human-approved Ready3 already has its separate original Ready cancellation API.

The store must opt into `permission_use_ready_cancellation_atomic_durable`; the default refuses and SQLite supplies the typed capture/commit ports. This narrow capability does not enable general durable permissions, HTTP permission cancellation or driver withdrawal of already-claimed work. Existing direct and controlled driver entry points retain their behavior.

1. Obtain real Ready2 through normal saved-permission authorization. Prefer issuing this operation before starting its driver; do not construct authority from a snapshot or revision.
2. Capture a coherent current view and exact `RunCancellationTarget`. Supply current catalog/context, dedicated management authority, monotonic facts and a bounded evidence account through `PermissionUseReadyCancellationRequest`. Current effect execution permission is separate from management authorization; an effect-gate revocation does not veto an authorized stop.
3. The producer proves the actual Use, inherited source, complete current Definition/binding and Ready relation. The Immediate writer independently rereads exact current fences and immutable physical evidence, then writes snapshot, thread revision and actual journal atomically. Treat only the actual confirmed result as Cancelled3. No callback signal or acknowledgement is needed for this Ready operation.
4. Retain any independent worker/capacity/store owners until they retire. This method does not drain an already-owned driver. If a real competing Dispatch claim wins before the Immediate reread, cancellation refuses without another write. The embedding must handle that actual work through a supported ownership path; it must not synthesize cancellation or replay a callback.

The tested late precommit journal fault proves full rollback to Ready2; guard removal permits a healthy request against the same target. An unknown Store error leaves the durable outcome unconfirmed and does not establish rollback, authorize automatic retry, or justify invoking the effect. After confirmed cancellation, repeat requests against the stale target refuse without another mutation.

Cancellation leaves the saved permission available to later normal runs, subject to their current application/policy/effect checks. The qualification closes/reopens SQLite normally and executes a fresh real NewUse to Complete4 while retaining previous authority/Use/history bytes. The actual contender control observes genuine driver entry before resuming the Ready request and retires that contender through the separately qualified entered-cancellation path.

Ready-state cancellation is distinct from withdrawing a claimed invocation that has not entered native code. That remaining driver integration, HTTP permission cancellation, recovery, deletion and broad lifecycle support are separate work. Existing finite input/envelope/account bounds apply; this scope makes no maximum-size or cross-platform claim. See [the scoped qualification](../../conformance/permissions/use-ready-cancellation/README.md) for executed evidence. Public metadata validation is recorded separately from actual runtime checks.
