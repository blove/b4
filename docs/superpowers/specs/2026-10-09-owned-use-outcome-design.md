# Owned NewUse outcome settlement design

Status: the narrow functional increment is adopted, 2026-10-20. Eight SQLite integration tests, fifteen protocol controls, static checks and the normal workspace regression passed on the reviewed local macOS arm64 source. See the [scope and qualification record](../../../conformance/permissions/use-outcome/README.md). Exhaustive Rust/std operation accounting, supported changing-resource/cancellation projection, Driver integration and recovery remain open. Broad permission capability remains false. The design below describes the ownership and transaction requirements; its presence alone grants no execution or qualification credit.

## Goal and approach

Persist the actual validated result of a genuine renewed NewUse callback without replaying that callback or accepting a caller-supplied replacement result. Build a distinct typed settlement path, then connect it to a profile Driver adapter in a later increment. The existing ordinary Runtime::complete_outcome delegates to the raw Store::commit guard and cannot serve as the permission-profile path.

Three possible approaches were considered. Removing the raw guard would expose arbitrary authority-bearing CommitPlans and violates the accepted design. Extending Dispatch's sealed write session would conflate a pre-callback claim with result settlement and change qualified behavior. A separate receipt-derived intent and Immediate writer preserves both boundaries and is selected.

## Ownership and entry

A non-cloneable PermissionUseOutcomeWork owns the entire PermissionUseCallbackReceipt, including genuine producer claim, current catalog/application, operation Store/authority anchors, actual result/error/panic payload and callback account. Conversion from Receipt to Work is consuming and nonfallible. It initializes a separate, fresh settlement account before any debit; it never replenishes or repurposes a callback or renewal account.

Settlement borrows Work mutably. Work retains its receipt through read, allocation, serialization, validation, SQL failure and return. Only callback status Settled, together with its retained validated EffectOutcome::Succeeded or EffectOutcome::Failed, can produce a private borrowed settlement request. The current direct NativeOutcome cannot produce Cancelled; CancelAttempt remains refused and unqualified until a genuine trusted cancellation/quiescence receipt is separately designed. No public factory accepts an EffectOutcome, invocation, claim fields, raw permission rows or arbitrary CommitPlan. Nonsettled statuses produce a fixed refusal and preserve their real error/result/payload until normal retirement. Uncertain or panic does not become a made-up FailAttempt. No callback is reachable from any settlement method.

The Store port returns an opaque PermissionUseOutcomeCommit, whose private success constructor is available only to a fully completed typed writer. A backend cannot publicly fabricate a successful StoredExecution response. Work validates the returned private seal against its request before recording successful completion locally and refusing a subsequent commit attempt. Errors do not imply rollback or commit success; they retain the receipt and expose the existing static error. A subsequent explicit call may retry result storage only. There is no automatic retry, receipt export, callback replay or success manufactured from an ambiguous return. Postcommit lost-response confirmation requires a separately reviewed protocol and stays open in the first healthy slice.

## Minimal reachable RED scaffold

First introduce the owned Work, a sealed borrowed PermissionUseOutcomeRequest, and an object-safe PermissionStore::commit_permission_use_outcome port with default UnsupportedProfile. Arc delegates the port. SqliteStore does not implement it yet, and existing guards remain literal. Request creation pays fresh inception and borrowed-carrier checks, only tests the genuine receipt status/result, and retains its actual permit. It does not manufacture an R4 observation or claim to validate storage provenance.

Use a concrete non-generic borrowed request with private fields: a retained loan of ApprovalResource, EffectInvocation, PermissionRuntimeUseWitness and producer origin; the renewed InvocationContext; the actual EffectOutcome; and borrowed trusted TransitionFacts. Append separately paid Claim/Permit sibling loans and a Receipt sibling request method in their owning modules. The Permit loan returns the retained Store borrow separately, preserving port object safety without trait-object erasure. All Store/authority/catalog/application anchors remain owned by Receipt.

The scaffold port exposes no raw outcome or authority fields to external callers. Backend progress is mediated by future sealed sessions. Private append-only sibling methods may borrow the actual retained Store without copying/exposing other claim fields. All original callback invoke/getter bodies, renewal/helper bodies and fields remain literal. The only existing-body exception is the explicit trait/Arc port declaration/delegation and module export linkage.

An independent sibling integration fixture starts from the already qualified real acceptance -> use -> Dispatch -> renewal -> callback path. Its callback returns the selected actual Bool(true)/empty-writes result exactly once. It consumes the actual receipt into Work and reaches the default unsupported typed settlement port. It captures complete typed/raw before and after storage, retains owners through the call, retires Work and all anchors, closes owner2, reopens owner3 and removes temporary storage before the intended success assertion. The expected RED is settlement still unsupported after genuine successful setup; missing API, compile failure, timeout, producer/renewal/callback refusal or cleanup failure is not that RED. No new backend implementation precedes independent acceptance of this actual RED.

## Green runtime and transaction

A later source stage introduces distinct outcome selectors, purpose-specific account/session and prepared work. Existing Dispatch RuntimeReadSession and terminal RenewalSourceSession cannot be reused as settlement seals: they pin different roles, source stages and Running/revision3 projections.

The initial green slice covers the selected single-task NewUse claim at unchanged owner/turn/resource fence. R4 reads the complete resource and durable retained use/source provenance using bounded length/type/header checks before payload decoding. It binds actual execution/task/effect/attempt/input, original claim owner/turn, thread incarnation, marker and retained use/source identity. Changed or foreign owners, attempts, turns, definitions, grants, permission sources or contradictory indexes refuse unchanged. Legitimate concurrent sibling/cancel changes require a subsequent explicit projection; the first slice conservatively refuses changed resources.

The settled callback result is already an external fact. Recording it does not request a new approval, create a new use, rerun the per-call constraint or invoke an authority inside SQL. Original/current anchors remain retained. Resource and authority provenance are independently checked; absence is not converted to new permission or human fallback.

Runtime reconstructs the actual existing KernelCommand::Complete or FailAttempt using the retained result and exact retained invocation, with trusted completion TransitionFacts. It computes the expected existing kernel transition from the matched current snapshot. The prepared intent binds the entire expected CommitPlan; the writer repeats command reconstruction and complete plan equality under Immediate. Sibling tasks, state/output writes, turn/history, attempt history, approved marker, definition/input, owner and all fences are validated, rather than recognizing status pairs. No arbitrary caller-supplied plan becomes authority.

The transaction independently rereads resource and every required original/current source range under one Immediate lock, validates all facts before the first update, then applies execution snapshot CAS, thread resource-revision CAS and actual completion journal insertion. No permission, grant, acceptance or use record changes. A late journal insertion failure rolls back preceding updates. Serialization/SQL parameters and decoded owners have their own cumulative accounting. A commit error remains ambiguous unless the backend can specifically establish precommit failure; the API does not pretend otherwise.

## Bounds, source review and qualification

Use a distinct immutable settlement budget purpose and cumulative checked byte/node limits. Determine production limits from the reviewed selected finite graph before execution; neither callback's 8 GiB logical allowance nor renewal's 64 MiB allowance funds new work. Fresh account creation, failure inception, every reached carrier/helper/primitive/codec/read/write and normal retirement need a complete accounting envelope. Existing record/depth/count/aggregate limits are preserved. Concrete compile-time carrier assertions establish actual operands/returns/closures and residual widths; they do not establish authority or runtime execution.

Scaffold source and genuine fixture are reviewed in a private current-tree copy. Freeze complete public/private maps, exact selected diffs, inverse guards, operators and evidence descriptors before formatting/compilation and then the explicitly selected native RED. Each new stage receives its own Source and fee eligibility. Prior callback qualification is setup provenance only; old binary addresses or passes are never transferred to the new source. Preserve actual command exit/reap/timeout and before/after evidence.

Each explicit attempt spends from the same cumulative Work account; failures never reset it. Retry capacity and per-attempt session admission must be independently priced before a retry control can run.

Green qualification includes actual result persistence/reopen, returned failure persistence, no replay after known precommit failure and explicit storage-only retry, stale/foreign fence refusal, mutated authority/source refusal, and late-journal rollback. Complete captured typed/raw table groups, owner retirement/reopen and directory removal precede final behavioral assertions. Lost-response idempotence, cancellation/parallel projection, recovery, nonsettled handling, human/legacy renewal and Driver scheduling remain separate increments.

## Protected scope

Keep old constructors, callback invoke/status/usage/outcome bodies, existing account limits, old renewal/Dispatch sessions and qualified fixtures literal. No change to KernelCommand variants, Snapshot version1 or validators, scheduler/driver signatures, schema/DDL, CLI defaults, TypeScript project, capability descriptor, raw mutation guard or historical registration support. No Git action is part of this local increment. Adopt only independently qualified code and truthful documentation; broad plan checkboxes stay open.
