# Settled permission-thread deletion — embedded design

The next remaining protocol gap is deleting a settled thread that contains persisted Always/Use records. RFC AP-003 and the existing generic fenced deletion establish the operation, while every current permission HTTP profile explicitly refuses it and generic SQLite deletion protects permission targets. Start with a dedicated embedded Rust/SQLite operation; HTTP and runnable exposure follow only after this narrow operation is verified. Continuous user authorization covers development and owned fixtures; never delete real user data during this work.

## Choice

Use a new explicit typed permission deletion API/Store declaration, with all existing generic permission guards and old APIs preserved. Relaxing generic deletion would silently broaden existing profiles and skip permission provenance validation. Building full recovery/deletion together would exceed a useful bounded increment. The dedicated operation lets an embedding explicitly authorize one captured thread incarnation and remove its complete settled physical history atomically.

## Supported state and authority

Only a coherent thread with an active execution whose status is Completed, Failed or Cancelled and whose entire owned execution history is settled is eligible. No Ready, WaitingForApproval, InFlight, CancelRequested, recovery-blocked or unknown live state is retired. Include actual original Always and genuine saved-use history, including no-entry and acknowledged/late-outcome cancelled forms already supported by the runtime. The API does not invoke callbacks, reduce results, reinterpret old outcomes or create Kernel transitions. No current effect constraint or new effect execution permission is needed to authorize destruction, but explicit current DeleteThread authority for the recorded actor/origin/route and exact target is mandatory.

Use ThreadDeletionTarget's existing captured generation/resource/active-ID/execution fence as the identity anchor. Its execution owner/revision must exactly match the stored historical snapshot. Legitimately settled prior-owner snapshots remain eligible after normal reopen; capture the separate current Store owner epoch and bind writer freshness to that owner. Do not apply live approval-fence/resource-capture rules requiring the historical execution owner to equal the current Store owner. A dedicated PermissionThreadDeletionAuthority receives the current bounded coherent resource and immutable context; do not borrow CancelRun/Dispatch authorization as deletion authority. Policy/authority runs outside backend/control locks. A runtime service captures the bounded complete resource, validates eligible relation, calls current deletion authority and constructs a non-deserializable prepared request. A new default-false PermissionStore durability declaration and separate capture/commit ports opt in; Arc delegation and real SQLite implement it. Success confirmation comes only after the actual atomic writer, bound to exact target/current owner and actual removed identities/counts. No callback or snapshot alone proves deletion success. Old stores remain unsupported by default.

## Complete bounded source and transaction

Capture the whole thread-owned physical set: thread, all owned execution snapshots, journal, approval grants/acceptances, permission acceptances/decisions/uses. Check both ownership directions so a foreign execution/dependent row or pointer cannot be removed or silently left dangling. Permission decisions have no SQL creator-execution column/FK: creator_execution_id exists in the record payload. Add an explicit guarded reverse payload-reference check for foreign-thread decisions claiming any owned creator execution, as well as the indexed reverse check for foreign Uses of owned permission IDs. Guard raw type/byte size and JSON/creator extraction before payload interpretation; relevant returned evidence stays bounded. If a foreign payload cannot safely rule out an owned creator because its required creator representation is malformed/oversize/unknown, refuse conservatively without writes. Do not silently skip such unknown rows. The query may visit unrelated foreign rows; these limits bound materialized evidence/decoding and do not claim a whole-database SQL scan/time bound. No schema migration, global owned in-memory decision table or new execution authority is introduced. Validate stored records against their own historical provenance and schema; do not require the latest catalog to reinterpret old calls just to delete settled records. Reuse existing snapshot/record decoders and pure relationship checks where applicable. Existing generic validate_thread_deletion also permits an active WaitingForApproval execution, so explicitly require every captured execution to be Completed, Failed or Cancelled. Existing deletion/grant/acceptance/journal SQL read loops are unbounded; reuse their pure validation logic through new bounded reads, not those loops unchanged. The source-fit review must identify exact reusable portions and new cross-record relations; no generic legacy guard relaxation.

Use a dedicated finite cumulative evidence account, bounded SQL row counts/bytes and record/JSON depth checks. The fixed operation limits are: 16 executions, 64 each of grants/approval acceptances/permission acceptances/decisions/uses, 512 journal rows, 64 MiB cumulative charged evidence and work and existing 65,536-node ceiling. Read LIMIT+1 and reject overflow without writes; check raw record/snapshot lengths before owned decoding. Charge both initial capture and writer recapture to the same account without refunds/resets. These are practical finite checks, not an exhaustive audit of Rust/std operations or claims that all maxima compose. Reviewer may refine constants to existing source limits with a concrete reason before implementation.

The SQLite writer owns one Immediate transaction, verifies schema-version/checksum metadata, captured current Store owner, exact thread target and complete source equality, repeats bounded eligibility/record relationships, clears active pointer, removes all dependent rows including all three permission tables plus existing approval/journal/execution rows, and finally removes the thread. Metadata/owner epoch and other threads remain untouched. Actual deleted row counts/absence must match the prepared source before commit. The normal Store open retains its existing exact schema-object verification; operation-time freshness uses metadata anchors and bounded concrete SQL, without adding a full schema-object scan that would prevent the established post-open injected-trigger fault test from reaching a late DELETE. Any mismatch, overflow or injected late delete error rolls back the entire transaction. No automatic storage retry, forced deletion of corruption, recovery, tombstones, background scan or cross-platform promise is added. Keep any existing durable generic deletion declaration separate from the new narrow declaration.

## Focused acceptance before implementation

Independently author four bounded real SQLite business tests using normal identifiers/inputs and genuine API provisioning: (1) complete original Always plus multiple genuine saved uses delete all owned records, preserve another thread byte-for-byte and allow healthy reopen; (2) actual cancelled original and saved-use histories, including real cooperative acknowledgement or retained late outcome, delete only after settlement and preserve output evidence until the deletion transaction; (3) current authority/origin, exact stale generation/resource/owner target, non-settled history, missing durability and finite overflow refuse without any physical mutation, with normal boundary controls; (4) exact late DELETE trigger failure after earlier dependent deletions proves complete physical rollback, trigger removal and a fresh successful control. Use real writer calls, no fabricated success or direct SQL provisioning of permissions. Adversarial stale/overflow/corruption fixtures may use clearly labeled SQL after normal owner retirement where necessary; preserve actual test counts/scope.

Runtime/Store-port local controls may prove default refusal, authority ordering and one cumulative account with small explicit error controls. They must not fabricate an atomic success confirmation. Every process/thread/wait has finite cleanup. Keep only focused cases needed for authority, atomicity, ownership and practical limits; no corruption matrix or speculative recovery audit.

## Delivery and continuation

After source/RED/quality gates and a fresh sequential implementation author, run focused SQLite/embedded regressions, format, strict workspace lint, compile and full locked/offline suite on one frozen source descriptor. Record actual counts/log hashes/process reaping separately from metadata. New source/qualification are opt-in embedded-only; current HTTP capabilities and example modes remain byte-identical. Adopt exact reviewed bytes with first backups and separate public metadata/integrity. Then connect the verified operation to a new explicit HTTP permission deletion profile in a later increment.

## Source-fit questions to resolve before plan

Identify whether existing PermissionAcceptance/Decision/Use decode_record permits historical normal identifiers under an appropriate dedicated budget without changing old profiles; how approval/grant/journal validators can be reused without their legacy permission refusal; how both-direction ownership checks cover permission decisions (thread-owned without execution ID), original acceptance versus later Use references, and cross-thread permission IDs; and how to represent a bounded complete deletion source/prepared/result without introducing a broad replay-capable authority object. Resolve these using actual source, not a new per-operation audit. No implementation starts before this small design has a concrete approved source fit.

## Embedding ownership precondition

The dedicated deletion authority includes the trusted embedding's per-thread exclusion and actual worker-quiescence precondition, held through commit/result. A terminal Store snapshot alone is not a physical worker-drain witness. This embedded API does not own a global run registry. Tests call it only after actual Driver/native joins; later HTTP wiring takes the existing ThreadClaim/owned mutation lease. No new SDK lease object or generic registry is added. This clarifies authority/host responsibilities and adds no public API signature, source feature or test matrix. Carry it into new API docs/runbook and final reviewed design delivery without mutating the active public baseline.

## Measured account refinement

The dedicated account uses a fixed 64 MiB cumulative byte allowance with the original 65,536-node ceiling. A bounded measurement of complete capture and writer recapture for the genuine sixteen-execution fixture exceeded the initial 16 MiB candidate. The new private operation marker changes only this operation’s effective byte ceiling; existing codec charges, old constructor profiles, row/record/depth limits and sticky exhaustion remain intact. This measurement motivates the finite allowance; it does not replace fresh production verification or promise every row-limit composition fits.
