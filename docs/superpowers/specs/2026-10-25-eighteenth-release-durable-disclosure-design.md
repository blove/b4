# T-018 durable approval before disclosure — private design proposal

Status: prospective, unapproved. This draft authorizes no code, controller, test, metadata, public release, M0 or compatibility claim. It is an input for independent design review and user approval.

## Contract and boundary

RFC `B4-RUST-RUNTIME-001` T-018 says a pending approval is durable before its prompt is disclosed. RFC §4.2 requires commit before disclosure; §§8 and 10 require the park snapshot, grant, resource revision and journal to commit together. `FND-K-003` has only a foundation-scope result for approval waiting before dispatch and sibling settlement. The existing `APR-ISSUE-001` and SQLite unit tests cover an atomic issue transaction and rollback. Existing HTTP tests cover stream interrupt projection and a reopened parked grant. None is a release proof that joins **real TCP disclosure**, a separate durable read, an aborted server process, and failed precommit writes on one frozen native application.

The proposed claim is one required-durable approval task on an immutable native application, owned SQLite and real loopback HTTP. A complete `interrupt` SSE frame and an authorized `GET pending_interrupts` response disclose only a grant already committed with the matching park snapshot, prompt, interrupt identity, resource revision and journal entry. Deliberately failed grant or journal inserts disclose no prompt or token. A hard-killed server cannot manufacture the grant after disclosure: a separately reopened store still contains the same committed record. This selected claim does not prove every crash point, general restart disclosure, all grant modes, arbitrary sibling schedules, resume, CP-009, M0, `COMPAT`, core or whole-product parity.

## Approaches considered

1. **Recommended: test-owned server child, rollback injection, and hard-kill/reopen.** An opt-in test child runs a native application and SQLite host. The parent owns bounded TCP reads and an independent read-only SQLite connection, injects precommit trigger failures in separate fixtures, and kills/reaps the child after the first complete disclosed interrupt. This exercises actual transport and process durability without production hooks. The extra child protocol and process cleanup need careful review.
2. **Single-process TCP plus SQLite reads.** Easier to author and diagnose, and a separate connection can witness a commit before response parsing. It cannot distinguish data that only survives while the server remains alive, so it is insufficient for the requested crash/reopen boundary.
3. **Production failpoint around approval commit.** It could force a precise interleaving but changes production behavior/configuration and expands the release surface. Use only if independent review finds a genuine untestable ordering gap in approach 1; any such change needs an amended design and new tests before release qualification.

## Proposed fixture and causal oracles

Use the existing opt-in `NativeHostConfig` and `HttpHost::new_with_application` with `RequiredDurable` approvals, one frozen route and one approval-required `Pure` task. Its ordinary and streaming effect callbacks panic if entered before a valid resume. Freeze the task input, prompt, route, policy revision and expected non-sensitive state separately from the response and database. The host uses a fixed authenticated principal and policy; permission for sensitive pending reads is explicit. Keep grant TTL, output, snapshot, journal, concurrent run, queue and input limits ample. Never put the token in an ordinary state response or diagnostic log.

The parent test starts each child with a dedicated private SQLite directory, a finite readiness channel and a bounded loopback listener. The child mode is explicit so spawning the test executable cannot recurse. The parent owns a panic-safe child guard, finite `try_wait`/kill/reap loop, and bounded socket, parser and database operations. A child crash is a real OS process termination; fixture cleanup must not retain a store owner or server socket. Each subcase has fresh threads/database state so a failed park cannot affect the healthy case.

**Failed precommit cases.** Use separate fresh child/store fixtures. In the first, install a test-only `BEFORE INSERT ON approval_grants` trigger that aborts the issue write. In the second, install a test-only `BEFORE INSERT ON journal WHEN NEW.status = '"waiting_for_approval"'` trigger that aborts only the park journal write; SQLite serializes `ExecutionStatus` as a JSON string in this column. Install either trigger before the POST only because the predicate cannot affect admission or Running journal inserts. An equivalent design could install the journal trigger after a deterministic Running gate, but that creates a race and is not the selected fixture. In both cases the independently read journal must show the same execution admitted and committed Running before the attempted park; a failure before Running is a test failure, never rollback success.

The negative POST oracle is fixed by the pinned HTTP path: after readiness the POST must be accepted as an HTTP 200 SSE stream, then that stream must close within a deadline without a complete `interrupt` or `done` frame. Heartbeat comments may appear within the bounded stream. A pre-admission error response, malformed headers, timeout, unbounded stream, or generic transport failure cannot pass. Inspect all captured wire bytes and diagnostics for the selected prompt and `b4ag_` token; neither may appear. A separate read-only SQLite connection must find no grant row or park journal entry and no `WaitingForApproval` snapshot for that task. Admission and Running bookkeeping must exist as above; the test does not demand those earlier rows vanish. After the stream closes, an authenticated and authorized `GET pending_interrupts` for the same thread must return HTTP 503 JSON with `details.code = "host_unready"` and no prompt or grant. This validates the fault gate, not an empty successful pending list. The worker sends readiness before task execution, the viewer response is 200 SSE, and a failed park faults control and closes viewers; any contradictory source or observed behavior requires design amendment before acceptance authorship.

**Successful disclosure.** In a fresh child/database, issue one POST stream. A bounded independent HTTP/chunk/SSE parser captures the first complete `interrupt` frame; it validates exact event syntax, one frozen prompt, one opaque grant, `resumeKey`, and linked interrupt identity. Before sending any resume, an independent read-only SQLite connection observes an unconsumed grant row, the matching task/interrupt/prompt/token and parking revision, a `WaitingForApproval` snapshot, the same thread generation and route, the incremented resource revision, and one coherent Park journal entry. The token is unpredictable, so the oracle compares its exact wire value to the separately read committed sensitive record while freezing every predictable field up front. An authorized `GET pending_interrupts` must return the same identity/prompt/grant with `cache-control: no-store`; an ordinary state read must not contain the token.

Kill and reap the server child after the complete interrupt has been observed, irrespective of whether the transport also delivered `done`. Reopen the same SQLite directory only after the child has exited; assert the store owner generation advances by one and the typed/raw park snapshot, grant, prompt, token and journal still match the prekill evidence. Do not invoke recovery or claim a successful post-restart pending HTTP read: preserving and re-disclosing the same pending identity after restart is T-019. The direct postkill SQLite read is the durability oracle for T-018.

The source review must trace `ApprovalService::park` → `commit_approval` → HTTP pending/interrupt projection and prove the response cannot be assembled from uncommitted in-memory data. The rollback cases close the complementary path: no commit, no disclosure. A real contradiction in that source order or an observed test failure requires design amendment before production repair, rather than weakening the oracle.

## Release and verification gates

- Author a reviewed exact implementation plan after this design is approved. It will name the acceptance file/helper boundary, child protocol, fixed command vectors, deadlines, parser caps, the source pins above, metadata path set, final regression categories and public checks. The T-017 post-acceptance map plus the independently reviewed catalog publication must be bound as predecessor bytes; no earlier T-017 receipt gains T-018 credit.
- Isolate source. Before any execution, independently review the complete formatted acceptance source, callback panic guards, child cleanup, raw SQLite oracle, response parser, trigger fault cases and complete workspace map. The failed child or trigger must not leak into the healthy fixture.
- Run the named T-018 test and strict relevant lint on the frozen map, then metadata RED/GREEN and a final current-map matrix including T-001–T-017 regressions. Require independent results, metadata, delivery, manifest and post-adoption public-integrity reviews before changing only T-018 to scoped `NATIVE`.
- A passing case may claim `native_approval_park_durable_before_disclosure_tcp_sqlite` only. T-019–T-056, M0, CP-001–010, current-HEAD TypeScript `COMPAT`, full core and whole-product parity remain open. Grant material in SQLite and backups remains sensitive; this slice makes no encryption or arbitrary hardware-failure claim.

## Decisions for review

The recommended approach uses a hard-killed test child plus two separately scoped precommit trigger failures. Independent review should confirm that the 200 SSE post-admission failure stream closes without `interrupt` or `done`, and that the healthy path exposes a complete interrupt before stream terminal in a way the parent can parse without assuming TCP packet boundaries. If either condition cannot be established without a production hook, revise this design before implementation. No implementation may start from this private draft alone.
