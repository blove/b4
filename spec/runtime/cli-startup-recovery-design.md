# Explicit native demo startup recovery design

Status: implemented and verified, 2026-10-03, for explicit fixed native demo CLI startup recovery. The accepted design was implemented and qualified through actual focused and CLI checks, macOS and Linux workspace runs, and post-support Python/contract checks. This status update preserves the original accepted design body; its narrow bridge and immutable final Source acceptance are recorded externally after this update. Follow the [completed implementation plan](../../docs/superpowers/plans/2026-10-03-cli-startup-recovery.md). The user authorized continuous Rust development; attached spec commands are reference material rather than tool authorization.

## User outcome and boundary

Add `b4run serve --demo --recover` as an explicit way to recover compatible saved native demo work before accepting ordinary requests. Existing `serve --demo` remains direct serving. The new flag selects the already qualified ordinary Preparing API, not startup confinement. The fixed demo application, routes, bearer authentication, current resource policy, durable approval configuration and signal ownership policy remain in force.

Accept `--demo --recover` and `--recover --demo` only for `serve` and `config-check`; reject duplicate, missing, foreign, fourth and non-UTF8 arguments before reading configuration. Represent serve selection with a new private Command::ServeRecover(Config); keep the existing Config shape. Config-check may retain its old command and no-effect validation after checking the flag grammar. This is a semantic boundary choice, not a claim that existing fixtures construct Config directly. The config-check form validates the same selection and existing environment without opening storage, advancing an owner, creating an executor or binding a socket. Help documents the flag; informational commands remain environment-independent. No additional environment variable, application loader, script upload or generic actor reconstruction is introduced.

The preceding startup-confinement receipt still excludes CLI exposure because it records its own historical embedding-only scope. This increment would expose ordinary preparation for the fixed server-owned demo identity only. It supplies no confinement authority, automatic incompatible-definition blocking, anonymous principal fallback, retry or force replay.

## Current evidence and options

`crates/b4-cli/src/process.rs` currently constructs an ordinary native HttpHost after strict private-directory validation, executor/signal setup, loopback binding and exclusive SQLite open. Its supervision closes admission synchronously, asks Axum to stop, then retains its executor, host and SQLite ownership until both actual registered-work quiescence and a successful outer-server completion witness exist. Lost transport or an opaque server panic retains ownership; a timeout reports progress without releasing resources.

The HTTP ordinary `begin_preparation` is synchronous inside an existing Tokio executor. It validates limits, registers the startup capability/owner and supervises the counted coordinator before returning a resource-free preparation handle. Preparing routers keep health available while readiness and ordinary admission are closed. Complete means recovery admission, not callback settlement. No changes to the HTTP, runtime, kernel, SQLite or supervisor algorithms are needed.

Options considered: changing `serve --demo` to recover implicitly would alter the current launch policy; a separate `recover` command would need an unnecessary stop-and-reopen gap; the explicit flag integrates the existing Preparing barrier and is selected.

## Trusted demo authority

The resolver recognizes only the selected server-controlled tuple application=native-demo, tenant=local, principal=owner. It returns a fixed currently configured Principal after all three stored labels match; it never constructs a Principal by copying arbitrary origin fields. Bearer tokens authenticate live requests and are not recovered from storage. Missing or foreign origins refuse through the existing resolver/recovery path. The exact immutable Definition and current Recover policy remain decisive. No persisted actor or secret generally becomes trusted merely because it is stored.

Keep this resolver in new CLI source with a pure, finite implementation and no Store, callback or private token capture. Do not change the ordinary OwnerPolicy body or HTTP Principal/Origin DTOs. Use existing bounded StartupPreparationLimits without claiming whole-startup heap, I/O or deadline bounds.

## Startup and process ownership

Select the old ordinary host path when the flag is absent and the existing Preparing constructor when present. A private internal holder may retain either host while providing the same router and shutdown handle. Construction failures retain the current fixed diagnostics and cleanup behavior before any native callback is started.

Start the outer listener and retain its task/witness before initiating preparation. Emit a fixed preparing marker for the explicit mode; the existing listening address remains a transport observation. Begin the ordinary preparation exactly once on the existing executor. Its observer is pure and must not retain resource aliases. Observe Pending repeatedly with bounded waits; Pending is not an error, cancellation, retry or evidence of resource retirement. Emit a fixed ready marker only after actual Complete; readiness itself remains enforced by the inherited router barrier.

A start error, wait error or Incomplete result closes admission and enters the same owned drain path. Distinguish the actual first trigger: a normal signal that wins during Pending must not become a Preparation failure merely because the shutdown cut later makes the coordinator finish Incomplete(Shutdown). After both witnesses, prefer existing HostFault for faulted Quiescent, then existing Server for real infrastructure faults, then a fixed Preparation error for an actual preparation-failure trigger, otherwise normal signal success. Lost transport remains nonreturning. SIGINT/SIGTERM and outer-server termination remain observable during preparation. A signal does not wait for readiness; startup work remains counted until its real returns. Startup failure returns a fixed nonzero diagnostic only after healthy-or-fault-classified normal quiescence and successful outer transport completion. Existing HostFault/infrastructure error precedence and opaque server-result retention must be kept explicit. Never drop a running executor to return a startup error. Never treat dropping the preparation observer as cancelling the coordinator. Complete does not permit early resource release while a recovered callback runs.

Prefer a narrow private first-trigger helper or equivalent reusable drain integration; do not duplicate or relax the established two-witness drain loop. Keep the actual Option<ServerResult> cache in the supervising drain owner scope. The helper receives borrowed access to that cache, stores a completed actual JoinError there before returning, and returns only pure trigger classification. No opaque server payload moves into a new outcome enum or a cancellation-sensitive temporary. Place the new process_startup.rs as a child of process so private Signals/ServerResult access needs no broad visibility changes; extract the post-trigger drain body once with an exact whole-file inverse. For absent mode, preserve the old trigger behavior, diagnostics and all existing test bodies. Any proposed drain refactor requires whole Source review and exact old-body inverses before adoption.

## Proposed qualification boundaries

A cleanly compiled baseline should refuse the new CLI spelling before feature implementation; that is meaningful flag RED only after normal fixture retirement. Preparation, authority and drain claims need their own actual checks rather than treating parser failure as coverage of later branches.

New parser/authority tests should cover both option orders and config-check, unchanged defaults, malformed arguments before environment access, fixed exact authority versus foreign fields, redacted diagnostics and empty-store startup. Real-process qualification should use ordinary legal native admissions and actual durable approval records, never fabricated owner/revision/accepted-grant rows. A compatible parked approval workflow must survive normal seed shutdown and explicit CLI restart with its entire grant/input/Definition/journal preserved; the real original approval should resume only its approved work. A legally admitted historical Definition absent from the fixed demo must yield closed readiness, static incomplete failure, unchanged selected work and normal drain. Signal during held startup/current policy work must keep executor and database ownership until explicit trusted work return. Readiness while a recovered callback is held must remain separate from callback settlement and retirement.

Use protected existing helpers where their visibility/contracts suffice; introduce finite new helpers otherwise. Raw whole original storage/authority captures and control addresses remain private; public support may contain safe counts, scopes and reviewed code hashes only.
