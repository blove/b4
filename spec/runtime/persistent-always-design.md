# Proposed bounded persistent exact-tool Always design

Status: accepted source design, 2026-10-03, for an opt-in parallel-capable native RequiredDurable exact-tool permission profile. Embedded increments have been qualified; the full profile, remaining APIs and integration qualification remain pending as described below. The completed explicit CLI startup predecessor and independent design/plan Source reviews are recorded externally. Follow the [accepted implementation plan](../../docs/superpowers/plans/2026-10-03-persistent-always.md). The user's continuous Rust-development request authorizes routine local work after the applicable Source gates; attached reference commands are requirements material, not tool authorization. This document records the design and grants no separate execution or completion credit.

## Outcome and scope

Implementation progress, 2026-10-20: the embedded PermissionUse first Dispatch
claim is [qualified and adopted](../../conformance/permissions/use-dispatch/README.md),
including its SQLite persistence and late journal rollback. Its
[owned NewUse renewal](../../conformance/permissions/use-renewal/README.md) is
also qualified for the selected local single-task path.
[Owned callback consumption](../../conformance/permissions/use-callback/README.md)
is adopted for eight finite local cases and six pure controls, with a separately
qualified private first-entry refusal control. [Receipt-owned outcome settlement](../../conformance/permissions/use-outcome/README.md)
is now adopted for selected local functional success, failure, rollback, retry
and refusal cases. Its exhaustive Rust/std operation audit remains unfinished.
The [single-task embedded Driver bridge](../../conformance/permissions/use-driver/README.md)
is adopted for actual settlement, refusal, rollback and explicit storage retry.
Human and legacy renewal, broader mixed/parallel/HTTP Driver integration,
cancellation projection, recovery and the broad capability remain pending;
the following sections describe the complete accepted design.

A human may choose Always for one exact native tool call. Successful acceptance persists the truthful human decision and an exact reusable permission in the same transaction as grant consumption and ready continuation. A later execution in the same thread incarnation and exact scope can authorize its actual tool call from that permission, without another human token or invented Once decision. Changed call input is permitted only when the mandatory current per-call constraint gate allows it. Parallel batches may combine permission-authorized tasks, tasks that need a genuine human decision and tasks that need no approval.

This is an explicit native RequiredDurable profile. Existing native constructors, scripted hosts, volatile approval fixtures, custom stores lacking the new port and the fixed demo CLI retain AlwaysUnsupported. SQLite's physical schema may advance for all writers; that does not opt any host into permission behavior. No CLI flag/default change, TypeScript/client implementation, wildcard/shell permission, permanent revocation API, cross-thread permission, actor reconstruction or complete core-profile claim is included.

The proposal deliberately binds more identity than the RFC minimum: immutable application revision, complete exact Definition, Definition-local EffectId and constraint revision join the application/tenant/principal/thread generation/route/policy/tool scope. Updating these bindings prompts again rather than silently broadening an old permission. Broad compatibility, optional/off approval modes, full RFC11.4, M0/CP010/broad56 and confinement qualification of this new authority remain unresolved.

## Existing facts and selected option

[RFC9.3](0001-agent-protocol-core.md#93-atomic-resume-acceptance) requires consumed grants, persisted decisions, permission effects and continuation intent to commit together; [RFC9.4](0001-agent-protocol-core.md#94-decision-and-scope-semantics) requires lasting exact-tool scope and current per-call constraints. [RFC11.1](0001-agent-protocol-core.md#111-one-database-and-one-owner) excludes a second attached WAL database as the atomicity boundary. These headings are semantic references; Source review binds the whole RFC and its numbered sections.

Current [application assembly](../../crates/b4-runtime/src/application/model.rs#L72) maps Definition-local EffectId to NativeEffect. It has no stable tool ID/revision or per-call tool constraint authority. Route InputValidator checks route input and supplies neither of those new contracts. [Exact registry selection](../../crates/b4-runtime/src/application/registry.rs#L65) already compares the complete selected Definition. [Approval validation](../../crates/b4-runtime/src/approval/validation.rs#L563) refuses Always, and accepted_once requires a consumed real grant plus a truthful old Once record. The [driver](../../crates/b4-runtime/src/driver/coordinator.rs#L260) parks every required unapproved Ready task. Merely allowing Always through Resume would approve one recorded call, not persist reusable permission.

A single-approval-task profile could reuse full parked Resume, but cannot honestly cover arbitrary mixed parallel batches. Enabling Always in every native application lacks the required trusted mapping and changes unsupported constructors. The selected profile adds a distinct typed Ready-to-authorized-Ready transition and PermissionUse provenance while keeping old construction and grant semantics.

All new API/type/table names below are proposed, not existing interfaces or accepted code. They need whole Source review before scaffold adoption. A standalone new kernel command/function is preferred over extending the public KernelCommand enum, so old exhaustive matches and Snapshot version 1 remain intact if meaningful validation proves the internal marker representation.

## Trusted catalog and pure per-call gate

Propose a separate immutable PermissionCatalog assembled around the same Arc<NativeApplication>, without adding fields to old RouteRegistration, EffectBinding, NativeHostConfig or ApprovalServiceConfig struct literals. Each entry binds an exact application identity/revision, complete selected Definition and EffectId to a new StableToolId, StableToolRevision and ToolConstraintRevision. Entries cannot be inferred from user metadata, prompt labels, routes alone, callback addresses, storage strings or client tokens. The initial catalog covers currently registered Definitions only. Existing NativeApplication::new_with_history rejects any requires_approval task in retained historical registrations; that constructor and its approval-free historical restrictions remain exact. This increment qualifies the currently selected approval Definition and healthy reopen with unchanged application revision. Historical approval registrations or remapping require a separate explicit proposal and Source exception.

Propose a mandatory ToolConstraint authority with a pure, finite validate-call entry. Before a claim, its new bounded call DTO receives the actual selected TaskRecord/spec/input with fresh trusted InvocationContext and exact catalog binding, without fabricating an attempt or EffectInvocation. After a claim, the actual won EffectInvocation must describe that exact call; the gate returns allow or a static refusal. It must not mutate business state, Store or permission rows, run the native callback or manufacture an actor. Application revision and resource policy remain independent checks. Changing implementation meaning requires a new tool/constraint revision, even if the application reuses an old string accidentally.

Every native effect installed in this opted-in profile must have one complete catalog binding and gate, including nonapproval effects. Permissions apply only to requires_approval tasks, but the gate cannot be bypassed by choosing Once, using existing permission, relying on an ordinary task, or recovering approved work. Catalog validation rejects missing/duplicate/ambiguous mappings, unknown effects, mismatched full Definitions, empty/control/oversize identities and a mismatch between the installed application and catalog. Proposed limits are 64 catalog entries and 64 total tasks per installed Definition; this is a new opt-in restriction, not a retroactive restriction on old applications.

Call the gate before permission authorization or acceptance of an allowing human decision, and again at dispatch against the actual won claim. Before each gate, ordinary resource authorization and trusted origin equality must succeed; after its return, refresh resource/fences and verify that the full selected binding/call remain identical. A constraint refusal or unavailable/panicking authority is decisive and cannot be converted into a human-approval fallback. Only a valid, gate-allowed call with genuinely absent/mismatched permission takes the ordinary genuine Park path; malformed permission authority is not an absence. A policy denial, missing Definition, unsupported binding, stale resource, panic or indeterminate Store outcome never creates permission or invokes a callback.

## Exact reusable scope

The permission scope is the exact tuple:

- ThreadId and ThreadGeneration, plus the full ThreadOrigin (application, tenant, principal).
- RouteKey, current resource-policy revision and immutable ApplicationIdentity revision.
- StableToolId, StableToolRevision and ToolConstraintRevision.
- Complete Definition equality and the selected Definition-local EffectId.

The stored record retains the complete bounded Definition. A canonical digest may index it, but a hit requires full equality against both the record and trusted registry selection; a digest alone is insufficient. Multiple task IDs invoking the same bound tool may reuse that permission when the scope and their actual calls pass the gate. Execution ID, owner epoch, resource revision, task ID, turn, attempt ID, input and proposal digest are per-use evidence/fences, not reusable scope. Otherwise permission could never apply across genuine future executions.

A permission is not a grant: the originating grant's TTL controls original human acceptance, not later permission expiry. Current policy revision mismatch/denial or gate refusal blocks use. Deny/cancelled applies to the submitted human continuation and does not silently revoke an earlier durable permission. The initial slice supplies no permanent revocation/update endpoint. Permissions are immutable, version 1 records with one exact scope; a legitimate later Always batch may reference an existing identical permission without overwriting its original source or any version referenced by a committed use. Capacity refusal happens before consuming any new grant, moving the park or writing continuation intent. The same exact still-pending set can subsequently choose Once/Deny through the proper old or combined path. No automatic garbage collection, source replacement, partial permission insertion, token refund or silent scope eviction is allowed.

## Durable records and bounded combined port

Propose PermissionStore: ApprovalStore as an explicit separate trusted port, with an independently declared durable_permissions capability, a bounded combined view and a typed atomic commit. approval_durable alone is insufficient. Propose new PermissionHttpHost<S: PermissionStore> and PreparingPermissionHttpHost<S: PermissionStore> wrapper types with their own new constructors/config wrapper requiring RequiredDurable approvals, permission durability, valid catalog/gates and all limits. They retain HttpHost<PermissionRuntimeStore<S>> only privately, with a new explicit profile Store adapter over the combined port, and expose their own router/shutdown/diagnostics and ordinary preparation surfaces, and provide no public inner-host getter, Deref, conversion or legacy ready-host escape. Preparation completion returns only the new permission wrapper. Old constructors do not infer opt-in from schema or trait availability. The ordinary fixed CLI keeps constructing its old host.

The combined view is read only after ordinary coherent ThreadView authorization. It includes the actual thread/execution, old grants/acceptances and new authority rows needed for this execution and exact thread scope. Every duplicated SQL index/record identity, generation, reference and stored version must agree; ambiguous or contradictory records refuse. Pure authorities/gates run outside the SQLite transaction. The port recomputes the exact kernel plan and row changes from typed mutation inputs under current fences, then commits them; a caller-supplied arbitrary approved snapshot is not permission authority.

Use three new tables in the same SQLite database:

| Proposed table | Truth represented | References and uniqueness |
| --- | --- | --- |
| permission_acceptances | One real full human pending-set batch containing at least one Always; exact Once/Always/Deny/cancelled-as-Deny decisions and consumed grant bindings | Target thread/generation/execution, original previous revision, new continuation turn; unique execution/turn and original continuation revision |
| permission_decisions | Immutable reusable exact-scope permission originally created by a real Always decision | Thread/generation, exact scope, original acceptance/decision/grant reference; unique exact scope and opaque PermissionId/version |
| permission_uses | One token-free authorization of an actual later required task from a permission | PermissionId/version, target thread/generation/execution/task/effect, original authorization revision/turn and internal marker; unique execution/task |

A mixed batch containing Always uses permission_acceptances for its entire truthful human decision set. Do not split it into partially committed batches or rewrite its Once/Always/Deny decisions into legacy approval_acceptances. All-Once/Deny batches may keep the old acceptance path, after the new profile's required gate checks. Opted-in dispatch accepts exactly one matching provenance: old consumed-grant Once, real consumed-grant decision in a new full human batch, or a valid PermissionUse. An absent/duplicate/conflicting provenance is not authorization.

Because legacy accessors must refuse targeted new authority, the combined port/bridge must also support genuine grant Issue/Park, pending/attachment projection, all-Once/Deny acceptance and Recover for an execution that already contains a PermissionUse or a new human batch. It preserves the existing real grant/token/full-set/Once-Deny semantics and old row formats, using typed combined mutations and separately reviewed pure validation helpers. It must not call a guarded legacy approval_view/commit_approval and then reinterpret that refusal. In a mixed execution, pending output includes only actual WaitingForApproval tasks with their genuine sensitive grants; approved internal markers are never projected. A legacy delegation is allowed only when fresh bounded classification proves the target has no new authority.

New record models are strict deny-unknown-fields, versioned and private-safe in Debug/errors. Reusable permissions retain the bounded full Definition but no callback pointer; uses retain actual proposal/input digests and exact policy/constraint revisions, not raw human tokens. The real GrantRecord remains the sole sensitive human grant. Existing required-mode prompt/token/verifier/TTL defaults and request framing remain unchanged. The recorded proposal digest binds the runtime TaskSpec/input/prompt only; it does not bind a current external business-object version unless the application supplies and validates that version in the actual call. Neither Always nor a digest promises an external-business-state lock or exactly-once side effects. Proposed per-operation bounds are 64 permissions per thread, 64 new human batches and 64 uses per execution, 65,536 bytes per acceptance/permission record, 16,384 bytes per use, depth 64, at most 16,384 structural nodes per new record and at most 8 MiB aggregate new authority bytes for the selected thread/execution view. Query at cap+1, check lengths/types and aggregate budget before allocating/decoding payloads. Existing approval/capture bounds remain in force independently; this proposal does not waive them or claim whole-database/process memory bounds.

Permission IDs/internal markers are opaque bounded new IDs, independent from approval tokens/resume keys. Strict record versions are 1 initially; record schema versions do not alter Snapshot version. Acceptance sources and uses must resolve to the actual full snapshots/journal revisions and recorded thread generation. Store commits validate cross-references before the first update and again via SQL CAS/constraints under one Immediate transaction. No authority callback, resolver or constraint runs inside that transaction.

## Human Always transaction

The opted-in resume entry retains the complete stable pending-set, exact route/Definition selection, owner/resource fences, original token/verifier/proposal/parking revision/TTL and current actor/policy checks. Duplicate, missing, extra, cancelled, denied and expired decisions retain their honest precedence; token replay never becomes a fabricated success. The gate must permit each allowing Once/Always call against the original exact task/call. Human Deny/cancelled consumes its genuine grant as Deny and creates no permission. Normalize cancelled before choosing the mixed-Always storage path; a batch without an actual Always decision stays a real Once/Deny batch.

For a batch with Always, one transaction conditionally consumes every required genuine grant, inserts the truthful full permission_acceptances record, creates or references exact permission_decisions, commits the real kernel Resume plan/new continuation turn and resource revision, and appends the actual journal intent. Previously permission-authorized or ordinary tasks in that parallel batch are preserved; the human decision set contains exactly the tasks actually WaitingForApproval. Repeated scope creation is insert-if-absent with exact equality, not destructive update. Within one parallel full human resume, distinct task/interrupt Always entries may resolve to the same exact reusable scope: retain every truthful distinct decision and consume every corresponding grant, but create/reference one permission. Choose original provenance deterministically from the first such task in declared Definition order, independent of submitted-array order, or reuse the already valid identical decision. Scope quotas count unique new scopes; duplicate same-tool tasks are not a conflict, partial continuation or reason to overwrite an immutable permission. Once the transaction succeeds, loss of response does not lose permission/intent, refund a grant or authorize an extra callback.

Any consumption, permission, acceptance, snapshot/resource-CAS or journal failure rolls back the entire batch. A Store error/panic after possible commit is indeterminate; reread by exact identity can establish actual committed state, but automatic retry/resume or invented success is forbidden. Reports distinguish confirmed commitment from ambiguous completion. The initial human-approved call derives its authority from that real acceptance, not from a made-up future PermissionUse.

## Token-free future authorization and parallel scheduling

Propose a standalone PermissionAuthorizationCommand/function in contract/kernel source. Its pure transition requires current Running without failure/drain, selected required unapproved Ready task, no prior interrupt/attempt/result/failure and a fresh unique internal marker. It changes only that task to approved Ready, installs PendingApproval {id: internal marker, prompt: null}, increments the snapshot revision/time and preserves the current durable turn/history. It spends no attempt, dispatches nothing and does not enter WaitingForApproval or require the globally parked set. The internal marker is an authorization identity, never a human grant, prompt or token; only actual WaitingForApproval tasks project human interrupts.

The new typed permission commit validates the matching exact permission and call, creates PermissionUse, CAS-updates execution/thread and appends the journal in that same transaction. Ordinary SqliteStore::commit receives an arbitrary CommitPlan, so routing only the new kernel command through this port is insufficient: before its first update, an explicit guard rejects a required unapproved Ready task gaining approval or a permission marker through any proposed destination, including forged approved InFlight. It also rejects newly installed permission markers, replacement/removal of existing marker/use identity or changed call/provenance-binding fields outside the typed combined mutation. A namespace alone is never authority. Raw legacy Store authority-bearing mutation of a targeted new-provenance execution is refused before updates; merely removing that guard so the new driver can finish is forbidden. The explicit profile adapter routes generic driver Start/Dispatch/Complete/FailAttempt/Cancel/CancelAttempt through a separate combined runtime-mutation transaction. This transaction reconstructs the exact allowed existing kernel command from candidate-owned facts/attempt/result and the matched current task, validates complete CommitPlan equality including sibling state, turn/owner/attempt history and fences, and strictly validates retained authority. Status pairs or a namespace alone are insufficient. It never mints new approval/use; fabricated authorization plans through raw ordinary commit or adapter commit both leave full storage unchanged. Resume, Park, Ready authorization and Recover remain explicit combined service transactions. Generic ordinary coherent read projection is separate from authority-bearing mutation: read APIs do not authorize execution, while profile mutation cannot delegate into a legacy-refusing port. Fenced cancellation uses the combined cancellation path with exact retained authority; fully validated fenced deletion/inspection remain their explicitly recognized storage operations. Legal completion/failure/cancellation must record already settled work without reinterpreting it as new permission or re-running a callback. Combined Recover preserves the same original authorization without resetting attempts. Ordinary owner/turn adoption of an execution with new provenance is refused; only the reviewed combined recovery mutation may perform it. Old Waiting-to-Ready real human acceptance and nonpermission recovery semantics remain distinct and protected. PermissionUse records the original previous/new revision, owner at authorization, current turn, selected task/effect, exact current proposal digest and scope/catalog/gate revisions. It binds the exact journal transition; a later recovered owner/turn may differ only through a genuine recorded recovery chain. It does not change or fabricate human acceptance/grant rows.

The existing DriverHost::park seam already returns StoredExecution, so the new bridge may return the atomically authorized Ready snapshot when a valid exact permission exists, otherwise the genuine Park snapshot. The generic driver trait/signature and scheduler body stay unchanged. Existing driver callback permits/attempt accounting remain decisive. Mixed batches must demonstrate that permission tasks can become approved Ready while unrelated pending tasks remain genuinely unapproved, without false pending tokens, starvation, capacity bypass or unintended batch settlement. Future execution uses a new actual ExecutionId and distinct PermissionUse; recovery/retries of the same approved task reuse that recorded authority and never create an extra use or permission.

Before callback, opted-in prepare_dispatch checks ordinary trusted resource authorization, full Definition/application/tool/constraint equality and the exclusive original authority provenance. It then obtains the unchanged durable Dispatch claim. Renewal reauthorizes the actual claimed resource, repeats the pure gate and validates the same source/use against that actual claim before exposing the callback. A renewal refusal retains the actual claimed attempt and follows existing owned cleanup; it invokes no callback and does not retry/refund. Cancellation and admission close continue to fence mutations, and all pure work/captured catalog, gate, application and store authorities remain counted until normal destruction. Panic and replacement panic-payload disposal stay inside the counted owner anchor before claims/leases/Shared retirement; Lost, deadline, future drop or an opaque join cannot manufacture quiescence.

This representation deliberately reuses Snapshot version 1's approved+interrupt invariant. Source/behavioral tests must prove strict existing validators accept the generated snapshot without weakening them and that every old projection excludes internal markers from pending/grant output. If that cannot be demonstrated, stop at a revised versioned snapshot proposal; do not loosen old validation or silently add fields.

## Recovery and legacy refusal

Opted-in known-ID recovery requires ordinary authorization before the bounded combined view, full original Definition/catalog equality, current policy and per-call constraints, original thread generation/resource/owner fences and strictly validated authority links. Recovery preserves real Always decisions, permissions and uses. Crash after human acceptance or PermissionUse commit but before callback retains the ready continuation intent; no grant/token is minted, refunded or treated as Once. Old-owner use provenance binds its original turn in turn_history and exact journal, rather than requiring current owner/revision/renewed turn to equal original authorization fences. Renewed dispatch binds its actual current attempt and resource/owner/turn fences through the genuine recorded Recover chain; it neither rewrites immutable original use authority nor rejects every legal next-owner use solely for the owner change.

The existing Recover policy remains decisive for in-flight work: Pure/Idempotent may return to Ready with the existing approved/use identity; Reconcilable/Unsafe remains outcome-unknown/blocked. No new retry, exactly-once side-effect promise or permission bypass of attempt budget is introduced. A missing or changed catalog cannot authorize an old historical Definition; stop unchanged through the existing recovery error path.

Legacy ApprovalStore/native hosts must refuse targeted new provenance before execution-owner recovery mutation or callback. A legitimate SQLite open may already have advanced the physical store owner epoch; refusal must not adopt or change the saved execution owner, turn, resource revision or any authority/journal row. Propose a narrow SQLite approval_view and commit_approval compatibility guard: after ordinary caller authorization, bounded-check targeted permission_acceptances/permission_uses (including both claimed execution and thread indexes), reject valid new authority with the existing static unsupported profile/Always error, and reject malformed/contradictory new rows as corruption. The new combined port uses separately reviewed internal readers, not the guarded legacy accessor. This guard must also precede legacy Recover/Issue/Accept commits under the transaction, so a host cannot adopt an execution then fail accepted_once. An unrelated permission elsewhere on the thread must not block legacy Once work. Qualify principal-first refusal on known-ID recovery, Preparing discovery, attachment/pending and dispatch; no profile disclosure may precede the existing ordinary actor/resource policy gate. A purported internal marker with missing/mismatched use is corruption under the opted-in profile, not proof of authorization. This is a narrowly proposed old-production exception, not a blanket change to old trusted Store/kernel behavior.

## Schema 4, migration, deletion and backup

Propose SQLite schema version 4 containing the three new tables with exact indexes/foreign relationships and the existing six tables unchanged. Save the exact current schema.sql as new schema-v3.sql; preserve schema-v1.sql/schema-v2.sql and migration-v2.sql/migration-v3.sql bytes. Migration-v4 adds the new objects without changing old row identities, generation, grants, acceptances, executions or journal. Fresh schema creation and migrated v3 schema must reconstruct the same exact DDL/checksum.

The current [version < SCHEMA_VERSION branch](../../crates/b4-sqlite/src/lib.rs#L951) runs migration-v3 and regenerates every thread generation. Split migrations by actual version: v1→v2→v3 once, v2→v3 once, v3→v4 without generation regeneration. Metadata/checksum change and owner advancement remain one transaction; unsupported/modified schema, trigger failure, invalid generation or overflow rolls back without advancing the owner or touching old rows. This is an unavoidable production-body exception. Record fresh v3 preservation and v1/v2 legal migration tests separately; a literal version bump is insufficient.

Fenced thread deletion validates both thread and execution indexes, strict row contents, all permission source/use references, generation and limits before updates. It atomically removes uses, permissions and new acceptance rows with old grants/acceptances/journal/executions/thread. Foreign claimed ownership, orphan/contradictory references, changed generation/resource fence or failed deletion rolls back every row. Identical-ID recreation gets a genuinely new generation and cannot inherit permission. Cancellation only clears outstanding unconsumed grants; accepted permission persists, while cancellation/admission controls block new use and callback.

Backup/checkpoint/restore carries all three tables in the same artifact and verifies exact schema 4/checksum and new strict authority records within stated bounds; no separate permission DB or post-copy patch. Schema 3 artifact support must be explicitly distinguished from schema 4 restore/migration, never interpreted by silently accepting current-only metadata. Destruction/ownership and source preservation still require normal return, all aliases absent and a genuine next writer; kill/abort cleanup supplies no retirement proof.

## Existing confinement stays conservative

No new permission authority is qualified for recovery confinement in this increment. Inside bounded SQLite capture/mutation, inspect strict targeted new acceptance/use records and their necessary permission/source links before entering the unchanged legacy authority audit. Valid new target authority returns UnsupportedAuthorityProfile with all rows and owner/resource/execution/journal state unchanged; malformed, foreign, contradictory or oversize records refuse as corruption/limit errors. Repeat classification inside the Immediate mutation transaction to prevent a race between capture and mutation.

Do not weaken legacy consumed-grant/Once/Deny checks, reinterpret missing authority as permission, or exempt new rows from bounds. Targeted real Always batches, mixed batches and PermissionUse all receive conservative refusal. Unrelated exact-scope permissions may coexist with an old Once target; their bounded structural integrity must be checked, but their existence alone does not reclassify that old authority. All permissions/new human batches/uses are preserved by any ordinary operation and legacy-target confinement. Both private and startup confinement paths must inherit this backend refusal, including AlreadyBlocked audits; do not return an already-blocked success without the new targeted check. Extending confinement's semantic authority audit is a separately qualified future slice.

## Honest capability descriptor 3

Keep CapabilityDescriptor 1 and CapabilityDescriptorV2 types, validation, old wire examples and old-host output unchanged, including always_permissions=false. Add a distinct strict CapabilityDescriptorV3 for opted-in hosts. It carries the existing truthful subset/readiness/drain limits plus always_permissions=true, independently durable_permissions=true and a required bounded_exact_native_tool permission-profile descriptor with the fixed scope contract, mandatory_per_call_constraints=true and actual configured finite limits. It advertises no tool catalog, private permission IDs, actor labels, grants or input digests.

Concrete proposed transport: the permission wrapper supplies a new endpoint adapter. Exact GET /b4/capabilities is handled exclusively by a new counted, authenticated ReadCapabilities policy/readiness/drain reader that serializes only CapabilityDescriptorV3; all other requests delegate to the unchanged ordinary transport endpoint. Wrong-method/foreign paths therefore keep the existing ordinary behavior rather than accidentally using a new route-generated 405. Do not serve v1/v2 as the complete installed permission profile, add discovery negotiation implicitly, or publicly expose the privately retained legacy router/host. The ordinary HttpHost router, transport and capability endpoint bodies remain exact. New preparation/router surfaces preserve this choice before and after readiness. The new capability job retains the same resource ownership/order, fault checks and no-Store-after-response-cut rules, and is separately qualified; copying static metadata alone is insufficient. Discovery itself preserves ordinary admission registration, authenticated valid-principal and immutable-application checks, current ReadCapabilities policy, readiness/fault cut and fixed error precedence/status/body behavior. Authentication failure stays 401, application-scope mismatch 404, policy refusal 403 and drain/unavailability 503 through the existing static helpers; infrastructure failures retain owned-fault semantics. Request diagnostics starts/finishes exactly once for the new capability branch, while delegated requests remain observed only by the unchanged old endpoint. No unauthenticated interception, duplicate diagnostics, credential/body parsing change or discovery bypass is allowed.

Version 3 is emitted only after the actual host assembly installs the new durable port, valid catalog and mandatory gates; SQLite schema 4 alone is not enough. Current required Once/Deny and known-ID recovery declarations must reflect the implemented new provenance paths, not anticipated support. Other unqualified features stay false, target_profile remains b4-ap-core/0, profile_status native_subset and core_profile_frozen=false. Missing/unknown nullable fields, inconsistent profile/durability/limits, unknown enums and unsupported versions reject strictly. Older v1/v2 consumers may reject the opted-in host's v3 response; no claim of client parity or implicit compatibility is made.
