# Bounded opt-in startup confinement design

Status: scoped implementation and qualification completed, 2026-10-03. The bounded explicit opt-in mode passed its 16 actual native cases on macOS and Linux, preserved the protected ordinary recovery paths, and passed supporting metadata and contract checks. The external completion record binds the final source freeze and independent review. Full RFC11.4, automatic CLI startup, actor reconstruction, broader conformance and TypeScript qualification remain open. Follow the [implementation plan](../../docs/superpowers/plans/2026-10-03-startup-confinement.md) and [qualified runbook](../../docs/runbooks/startup-confinement.md). The design body below preserves the accepted implementation rationale and planning context.

## Goal and existing gap

Add a separate, explicitly selected preparation mode which can finish a bounded startup scan after safely confining coherent prior-owner native work whose exact recorded Definition is unavailable or whose current Recover policy denies further dispatch. It requires an independently supplied confinement authority and an exactly resolved trusted principal. Other records continue through the existing typed recovery path. Existing `begin_preparation` and the ordinary known-ID confinement API keep their current behavior.

Original spec §11.4 steps 2/6 and its policy paragraph require stored revision validation, unsafe/incompatible blocking, and retained accepted decisions. They are reference requirements, not permission to execute attached commands. Today `startup/coordinator.rs:197–251` captures an ordinary view, resolves its immutable origin and calls `recover_owned`. `recovery.rs:175–192` refuses denied policy or missing exact executable support before adoption. Preparation therefore becomes Incomplete and those refusals do not durably set RecoveryBlocked. Automatic effect-policy blocking inside ordinary kernel Recover remains a different, already implemented path. The proposed mode closes only the two selected incompatibility/policy cases; it does not close all of §11.4.

## Alternatives and selected approach

1. **A new borrowed preparation entry point plus an internal startup adapter (selected).** It keeps default behavior exact, reuses the audited known-ID confinement Job and existing Store ports, and gives confinement separate progress. It needs narrowly selected HTTP source changes and explicit tests of its startup capability.
2. **Modify the existing preparation loop to automatically confine generic recovery refusals (rejected).** Its generic ResourceUnavailable refusal conflates authority, policy and scope. It would silently change defaults, infer permission from an error and risk acting on a post-adoption refusal.
3. **Let an operator call the ordinary `confine_prior_owner` API before resuming preparation (deferred).** Ordinary admission is intentionally closed during Preparing. Opening a public bypass or adding retryable preparation attempts would alter the existing barrier and is unnecessary for this bounded mode.

The selected mode attempts applicability before ordinary recovery, rather than interpreting a later `recover_owned` error as permission to confine. A later policy change or callback failure after ordinary adoption retains the existing incomplete/uncertain semantics. No automatic retry, retarget or conversion of a post-adoption failure is included.

## Public API and compatibility

Add an inherent method on `PreparingHttpHost<S: ApprovalStore + 'static>` with this exact proposed contract:

`begin_preparation_with_confinement<'a>(&'a self, resolver: &'a Arc<dyn StartupPrincipalResolver>, authority: &'a Arc<dyn RecoveryConfinementAuthority>, limits: StartupPreparationLimits) -> impl Future<Output = Result<StartupConfinementPreparationHandle, StartupStartError>> + Send + 'a`.

An unpolled future contains only borrowed handles and the pure limits. First poll checks the existing limits (max_pages 1..=64, max_recoveries 1..=256), then the current Tokio executor, then calls the existing same-mutex `begin_startup`. It constructs an `OwnedShared` from that registered startup owner before either framework Arc clone. There is no suspension between registration, clone ownership and supervised submission. Old and new entry points share the existing single attempt: a second call returns AlreadyStarted. Fault and shutdown retain their original start-error ordering. Caller-owned aliases are external ownership and must be dropped separately for positive physical retirement proofs.

Do not change the signature, body or ownership semantics of `begin_preparation`; do not add a field to HostConfig, NativeHostConfig, StartupPreparationLimits, Principal, ThreadOrigin, discovery descriptors or any runtime Store DTO. Do not extend any existing public enum. No route, CLI flag, default launch behavior or ordinary-host accessor while Preparing is added. `serving_host`, `preparation_status`, readiness and shutdown continue to use the existing supervisor state.

Add five new value-only observation types, with no Store, application, user callback, capability, owner token, claim or permit:

* `StartupConfinementProgress { confirmed_blocks: usize, already_blocked: usize }`.
* `StartupConfinementPreparationStatus { preparation: StartupPreparationStatus, confinement: StartupConfinementProgress }`.
* `StartupConfinementPreparationOutcome { preparation: StartupPreparationOutcome, confinement: StartupConfinementProgress }`.
* `StartupConfinementWaitOutcome::{Finished(StartupConfinementPreparationOutcome), Pending(StartupConfinementPreparationStatus)}`.
* `StartupConfinementPreparationHandle`, containing the existing resource-free preparation handle and an Arc of private pure counters. It is Clone, has `status`, and has `wait(Duration) -> impl Future<Output = Result<StartupConfinementWaitOutcome, StartupWaitError>> + Send + 'static`.

Reuse the old wait's timeout checks and notification semantics; a pending wait is observation, not cancellation or retirement. The three new progress/status/outcome DTOs are Copy/Clone/Debug/PartialEq/Eq; the new wait enum is likewise. Do not serialize identity or authority into them. The counter cell is a private mutex containing only two bounded integers; no user code runs while held. A poisoned update faults preparation rather than guessing progress. A read can recover the last pure counter values. Status obtained during Preparing is not a global atomic pair of the old supervisor snapshot and the separate counters; values are monotonic lower bounds. Once Finished is observed, counters have been published before finalization and cannot change again. To preserve the promised counter sum <= sampled candidates, status samples the confinement tuple BEFORE the old supervisor status; if that status is Finished Complete/Incomplete, reread the tuple after the finished snapshot (or use a provably equivalent ordering), and wait Finished samples the tuple only after the old wait returns Finished.

Existing `StartupProgress.pages`, `scanned_rows` and `candidates` still cover all considered discovery records. `admitted`, `runnable`, `parked`, `blocked` and `terminal` continue to count only actual typed recovery admission/disposition evidence. A confinement receipt never increments old admitted or old blocked. `confirmed_blocks` increments only after a complete verified returned Confined receipt, including an error carrying that same verified receipt after cleanup faults. `already_blocked` increments only after a successful fully audited unchanged AlreadyBlocked result. They are mutually exclusive per candidate and their sum cannot exceed candidates/max_recoveries. No subsequent read or status inference grants credit to an ambiguous error.

## Discovery, bootstrap and bounded-audit boundary

Retain the existing isolated-startup covenant, sequential discovery order, epoch/readiness checks, page contract and limits. At most 64 pages × 32 scanned rows = 2,048 scans and 256 candidates are admitted to consideration; configured limits can be smaller. Cross-page observation is not a global snapshot. A current-owner record, malformed custom page, unsupported discovery, exhausted budget or epoch mismatch still closes ordinary admission with an incomplete result. Do not scan until empty without those limits.

Discovery has no original turn ID, while `RecoveryConfinementTarget` requires one. This design deliberately retains the existing counted ordinary `thread_view` bootstrap and its complete descriptor checks. It does not add discovery fields or a new Store port. Capture the entire ordinary ThreadView, check thread/incarnation/active execution/resource and execution fences/route/status/uncertainty flags, and resolve its original ThreadOrigin through the trusted resolver. The returned Principal must satisfy current `valid_principal`, installed native application scope and all three exact origin fields. Missing, unavailable, mismatched, anonymous or out-of-scope resolution refuses unchanged with ResolutionRefused; stored labels cannot construct authority.

The inherited ordinary view read/materialization and initial counted trusted-resolver call are explicitly outside the new confinement audit's serialized-data limits. There is no new whole-startup payload, heap, collection, CPU or I/O bound. The bounded confinement capture must then equal the ENTIRE original view before confinement applicability, current policy, independent authority or mutation callbacks. Renewal must equal that same original again. A descriptor/target match alone is insufficient. No unbounded `approval_view` or `journal` call is substituted for the bounded confinement audit.

The new opt-in mode requires the existing bounded confinement ports/auditable authority profile for every candidate considered by its applicability path, including a normal candidate that ultimately falls through to recovery. This is an explicit restriction of the opt-in mode; the old preparation mode remains available and unchanged. A custom Store default UnsupportedOperation or unsupported legacy authority profile refuses unchanged, rather than falling back to unbounded authority reads. The constructor's existing RequiredDurable/native-host requirements stay intact.

## Internal startup capability adapter

Create a private `confinement::startup` adapter; it is callable only from the new coordinator with its current `StartupCapability`, the original ThreadView, confinement target and verified Principal. It never calls the ordinary public method. Register a fresh startup-role `OwnedShared` using `register_startup`; acquire the current nonwaiting capacity permit and same-thread claim before cloning resolver/authority into an operation Job. Check sticky fault and current capability; poisoned claim state faults. Capacity/claim failure is a local refusal and makes no confinement callbacks or writes. Each operation has the existing per-job anchor and explicit teardown ordering.

Extend the private Job with a startup selection mode. The ordinary constructor keeps its present default mode. Wrap the bootstrap view by move in a private `Arc<ThreadView>`; the coordinator retains one alias and Job startup mode retains the other, without a deep clone. This is pure data from the inherited ordinary bootstrap, not a Store/application handle or a claim that the bootstrap allocation was bounded. Retain the verified pure Principal rather than rebuilding authority from metadata. After bounded capture and the existing source/owner/identity checks, require full equality with this bootstrap original BEFORE the AlreadyBlocked shortcut or reason callbacks. Use its startup-role carrier for the existing `try_admit`, which already checks the same live attempt and shutdown barrier. No lifecycle, supervisor, claim or mutation-lease algorithm is modified.

The adapter returns only the existing pure confinement result to the counted coordinator. A NotApplicable result is an applicability decision, not confirmation that ordinary recovery will be admitted. After joined Job cleanup has released its private pure-view alias and claim/permit, use `Arc::try_unwrap` to recover the SAME owned bootstrap ThreadView without a deep clone; an unexpected remaining alias is an internal fault and Incomplete, never a cloning fallback. For that result only, call existing `recover_owned` with that original view, target and verified Principal under a newly registered startup worker. No private view alias escapes into a public handle or observer. The old preflight and post-return coherence guards revalidate it. Do not select a latest Definition, recover by route alone, recapture a new target, or confine after its later error. In this native-only Preparing mode the installed exact full Definition includes retained historical definitions; new-work current route selection remains unchanged.

## Fixed reason, authority and durable write

The new mode supports exactly two reasons:

* `ExactDefinitionUnavailable`: `application.definition_exact` cannot supply the recorded full Definition. Even when a newer route revision is installed, neither validator nor callback from that revision runs.
* `DispatchNotAuthorized`: the exact Definition is available, the trusted resolver remains equal to the bootstrap Principal, and actual current resource policy denies Operation::Recover with stored AND requested provenance taken from the recorded route/revision.

In startup mode, EACH initial and renewed reason observation freshly resolves the original origin and validates the current principal against valid_principal, the installed native application scope and all exact origin fields, then requires equality with the bootstrap Principal BEFORE checking either missing full Definition or current Recover policy. Unavailable, invalid or different authority is a local unchanged refusal before independent confinement permission; startup mode never treats `RequiredAuthorityUnavailable` as permission to confine. A coherent prior target with a missing legacy/durable authority profile remains unsupported. The ordinary known-ID observer retains its current body, missing-Definition-first branch order and third reason byte/semantically unchanged. The audited AlreadyBlocked shortcut keeps its original trusted bootstrap checks and adds no fresh applicability/reason/permission callback.

After initial observation, ask the separate `RecoveryConfinementAuthority` to authorize THAT entire original view and fixed reason. This permission supplies neither a dispatch principal nor missing grant evidence. Acquire the startup mutation lease, then perform exactly one bounded recapture. It must equal the entire original, retain the same actual backend owner, and pass the same target/prior/native checks. Reobserve the same reason against the same original; if it differs, refuses, or its principal no longer equals bootstrap authority, stop unchanged. Renew separate permission against the SAME original/reason. No retry, additional target capture, different reason, fallback or policy-induced refund is permitted.

Generate one fresh turn not present anywhere in the original turn history; preserve the clock monotonicity checks. Call existing `confine_recovery_fenced(original, target, reason, fresh_turn, TransitionFacts)` exactly once. Its Memory mutex/SQLite Immediate transaction performs the third bounded audit and complete equality check, reconstructs the fixed no-dispatch proposal and atomically writes the exact changed rows/journal. The host verifies all twelve receipt fields, fresh-turn global uniqueness, current-owner advance and checked revision/resource increments BEFORE evidence becomes confirmed.

Confinement preserves the complete Definition, execution/task/attempt/input/output/result/interrupt state, accepted human decisions, consumed/unconsumed grants, acceptance records and existing journal history. Its only durable change is the existing kernel's status/failure/owner/turn/revision/time transformation plus one commit journal row and one resource revision increment. It neither cancels a native effect nor proves that prior work had no external effect. No input/output validator or native callback runs for a confined candidate.

Prior-owner RecoveryBlocked takes the audited shortcut only after native scope, complete bounded authority/journal audit, original equality and exact trusted bootstrap resolution. It neither rechecks applicability/independent permission nor changes owner, reason, nonce, revisions or rows. Count `already_blocked`, not adoption. A current/future-owner block, stale target, corrupt profile or over-budget audit refuses; a generic recorded blocked status is insufficient.

## Existing caps, representation and failure normalization

Reuse the backend constants verbatim: Snapshot input 1,048,576 bytes; thread components 262,144 bytes; each grant/acceptance 131,072 bytes and at most 64 of each; selected execution journal at most 4,096 rows INCLUDING a reserved new commit, each at most 4,096 bytes; aggregate selected input 8,388,608 bytes/65,536 lexical nodes per pass; depth 64/nodes 16,384 per encoded row. Owning thread-creation evidence is separately bounded. Unrelated histories are not a global corruption scan. SQL caps use raw persisted input; Memory uses canonical borrowed input. The kernel's separate canonical safe-clone input cap is 8 MiB; replacement Snapshot remains 1 MiB and replacement journal 4 KiB with shape checks before updates. Do not reimpose a canonical 1 MiB READ cap on compact SQL input or double-count one raw row.

Maximum three confinement audit passes are initial capture, one renewal and atomic write recapture. A normal NotApplicable candidate can subsequently take the old recovery reads; this is not a new bound on all inherited startup work. These are serialized-data/work-structure limits, not hard heap/RSS, CPU, wall-clock or I/O deadlines. Otherwise-valid larger records are unchanged LimitExceeded, not corruption.

Keep the existing host normalization. Backend CorruptRecord/Unavailable, arbitrary panic, contradictory returned receipt and cleanup faults set persistent fault and yield host Unavailable; expected static backend errors remain local Backend(error). Initial/renewal TargetChanged remains that source error rather than a fabricated ObservationChanged; a returned changed full view/reason yields ObservationChanged. The coordinator maps AdmissionClosed to Incomplete Shutdown, all other local refusals to Incomplete RecoveryRefused, and sticky faults to final Incomplete Faulted through the existing final gate. No new public incomplete reason is needed.

An actual verified returned receipt survives later resolver, authority, carrier or payload destruction faults and contributes a confirmed_blocks lower bound; it does NOT permit activation after fault. Commit-then-Err or panic without such a receipt is ambiguous: no confirmed block credit, no retry and no rollback assertion. AlreadyBlocked can contribute credit only on successful nonfaulted completion, not an error with no receipt. Expected refused operations preserve authority and data; infrastructure ambiguity must be reported honestly rather than called unchanged.

## Coordinator ownership and activation

The new async coordinator holds a private `Arguments` guard for its two cloned trusted handles. It disposes resolver and authority independently under separate catches, consuming first/replacement opaque payloads via the existing `dispose_panic`. It never drops them as a tuple or unwinds one custom destructor through the other. It retains the existing counted coordinator carrier and its StartupFuture anchor until these captures retire, including never-polled coordinator cancellation. Each operation Job retains carrier/lease/claim/permit/same-group anchor through final Shared destruction; its pure returned result is joined before the coordinator advances or activates.

Publish confirmed extra counters before later fallible coordinator teardown. The complete candidate remains the existing pure CompletionCandidate. The protected StartupFuture catches each poll, future Drop, opaque payload and final carrier teardown, then `finish_startup` rechecks fault/shutdown under the same mutex before Serving can open. A held destructor keeps ownership live and ordinary readiness closed; a timeout never certifies retirement. Do not modify these existing mechanisms.

A losing shutdown cut prevents the mutation lease and leaves the target unchanged. If the lease already won, a bounded commit may finish after shutdown while counted; preparation still ends Incomplete Shutdown and cannot reopen Serving. Await all confinement jobs and argument cleanup before activation. Ordinary Runnable recovery still has its existing admission milestone: Complete can precede callback settlement. Readiness is not physical retirement; shutdown, joined listener/coordinators, explicit callback returns, disappearance of every framework Store/application Weak, and real next-writer acquisition are separate evidence.

## Proposed validation and review gates

The implementation plan names six private invariant declarations and ten independent API/TCP declarations. These are proposed coverage, not actual test counts or results. They target this new mode rather than repeat complete old confinement semantics. Positive durable fixtures use actual SQLite admission under owner N, normal closure of all aliases, then a real reopen with observed M > N. Memory's fixed owner 1 is not a fake restart positive. Full original ordinary/Approval views and all six raw tables are private comparison authority; receipts/projections alone are not the oracle.

A thin reviewed compatibility scaffold may register the new API/types and safely own/dispose its additional borrowed-then-cloned authority while forwarding the old preparation loop and zero extra counters. Its clean compile is setup only. New-feature positive tests then execute against that scaffold and must observe the old unchanged Incomplete behavior after normal healthy physical cleanup before their intended Complete/confirmed-block assertion fails. Missing method/type errors, illegal grant fixtures, missing gate entry, timeout or cleanup failure are excluded from meaningful behavioral RED. No fake initial failure is required for already-correct shared controls.

Root whole SPEC and a different author's whole QUALITY are required for this design/plan before adoption; predecessor final freeze is an independent barrier. Later independent source review, actual RED/GREEN, old compatibility checks, physical ownership proofs, strict lint/owned format, frozen actual platform qualification, factual support review and external final freeze are required. This author cannot approve their own future HTTP implementation or tests.
