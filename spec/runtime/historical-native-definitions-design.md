# Explicit retained native Definitions

Status: accepted design, 2026-10-02, after whole specification and independent quality review. Implementation and qualification follow the [implementation plan](../../docs/superpowers/plans/2026-10-02-historical-native-definitions.md). The predecessor bounded startup preparation increment is verified. The evidence below is planned for this increment.

## Outcome and limits

Offer an explicit immutable current-plus-historical native assembly. New work selects a declared current registration. A continuation selects only its recorded route, execution revision and complete Definition, using that registration's own callback bindings, validator and output kinds. No latest-version fallback, semver ordering, callback introspection, hot replacement, migration, second driver or new persisted field is introduced.

This is a bounded RFC11.5 historical drain capability. Original RFC11.4 still requires durable incompatible/revoked-policy confinement and other restart behavior outside this slice. Missing support keeps the existing healthy no-mutation known-ID refusal and startup Incomplete, rather than manufacturing RecoveryBlocked, a principal, a fence or a policy decision. Current-owner work and unsafe/reconcilable uncertainty retain their existing semantics. Pure/Idempotent remain trusted declarations, not external exactly-once evidence.

## Additive portable API

Use the existing RouteRegistration unchanged. Proposed methods:

```rust
impl NativeApplication {
    pub fn new_with_history(
        identity: ApplicationIdentity,
        current: Vec<RouteRegistration>,
        historical: Vec<RouteRegistration>,
    ) -> Result<Self, ApplicationConfigError>;

    pub fn definition_exact(&self, recorded: &Definition) -> Option<&Definition>;
}
```

`new`, `identity`, `definitions` and `definition(route)` retain their exact current-only meanings. Old `new` still rejects duplicate RouteKey values and installs no history. `definitions()` is current-only; unchanged HTTP collection therefore cannot collapse retained versions. `definition_exact` checks the route/revision pair and then whole Definition equality. A matching revision label with altered batches, task recovery/approval policy, effect identity/order or attempt budget is unavailable.

Keep current nonempty, with at most64 current registrations and exactly one current entry per current RouteKey. Historical may be empty; the combined current-plus-historical count must be <=64. Keep the existing <=64 batches, tasks, bindings and attempts checks per Definition and its complete kernel validation. Check counts before building maps. Validate every registration before publishing the application; invoke no callback/validator and open no Store during assembly.

Use separate current RouteKey and retained (RouteKey,ExecutionRevision) tables, or an equivalent exact immutable representation. All route/revision pairs across both tables must be unique. Reject a historical pair equal to a current pair even if its whole content or bindings differ; reject duplicate historical pairs even if equal. Revision ordering never chooses current. Historical-only removed routes are permitted within the same aggregate bound: exact continuation can find them, while `definition(route)`, `definitions()` and new HTTP work cannot. Current stays nonempty so host assembly retains the existing minimum configuration.

Reject every historical registration having ANY declared requires_approval task, including an uninitialized future batch, with static ApplicationConfigError text such as historical_approval_unsupported. Do not reject approval-bearing current registrations. Additional static configuration reasons can use existing ApplicationConfigError; preserve the old constructor's error order and strings. NativeOutcome, ControlledNativeOutcome, InvocationContext and existing invocation/input error enums receive no new fields or variants.

The private selected registration helper serves validate_input, output_kind and both invoke methods. Each exact retained registration supplies its own effects and optional validator; EffectId is never globally resolved or taken from current merely because its spelling matches. Cooperative observer/output checks and existing context/membership/owner validation remain the same.

## Installed assembly and recorded execution revisions

InvocationContext.application_revision is the installed NativeApplication.identity().revision, including when this assembly embeds a v1 executable registration alongside current v2. InvocationContext.execution_revision is the exact selected recorded Definition.revision. The immutable origin must still match the installed application's application label and the separately trusted actor/tenant.

The Store does not persist an original application assembly revision. Do not invent one or add a historical assembly-revision field. A retained v1 callback in installed assembly-v2 therefore receives application_revision=assembly-v2 and execution_revision=v1. Changing callbacks, validator, output kind or behavior requires a newly declared execution revision; replacing the installed assembly requires a new application revision. Matching labels cannot prove identical executable binaries across deployments; that remains a trusted embedding obligation.

## HTTP selection and authority

Keep Shared.routes as the current map. Introduce one private recorded-definition selector shared by recovery, resume, attachment and ApprovalBridge authority. It receives the immutable native application explicitly (or an equivalently explicit registry carrier), calls definition_exact and constructs RegisteredRoute::native only on exact support. Scripted selection keeps route lookup plus whole Definition equality. Never use current route-only fallback for recorded native work, including historical-only removed routes.

Both recovery preflight and its later selected route lookup use this helper, after ordinary origin/scope/policy renewal. Preserve the original coherent view, generation, active relationship, resource/execution fences and complete Definition across waits and the existing atomic approval recovery transaction. The driver already receives a RegisteredRoute and uses its exact Definition for invocation, membership, output kind and installed context; no second effect loop or worker ownership change is necessary.

Transport run selection stays current-only. Initial Resume policy provenance needs a careful bounded correction: the existing counted Store/policy job reads the ordinary view before calling policy. Derive valid resume requested provenance and exact-support/static selection metadata THERE from the captured execution's exact recorded Definition when its route matches the requested route. Return only the resource-free original ThreadView, recorded requested provenance and support/static metadata from this job; never return RegisteredRoute, NativeApplication, callback/validator captures or Store handles through its JoinHandle. OwnedShared::spawn retires its counted carrier before returning the result, so a resource-bearing result could survive request abandonment outside that job's ownership. After awaiting the pure result, reselect the exact immutable registration while the endpoint's OwnedShared remains alive, retain the original coherent view through renewal, and move the selected registration/captures into the existing counted worker carrier. Do not authorize an old valid resume using current v2 provenance before obtaining the view. Route mismatch/missing support still goes through existing ordinary authority and static protected refusal; no mismatching requested route can select the current executable as a substitute. Preserve current-only wrong-route/error behavior with existing historical tests and dedicated new policy-context regressions. Add a scoped abandonment/held-capture regression: abandon a historical resume request while its trusted policy job is held and its v1 application callbacks/validator transitively retain the real SqliteStore; prove Store/application Weak references and actual writer AlreadyOwned remain until explicit nonexpired return and counted capture retirement, then normal Quiescent and real writer owner+1. No returned registration capture may outlive that counted carrier, and timeout or a dropped request is never retirement evidence.

Attachment's registered check also uses the exact helper. Its unchanged original publisher capture, full view/Definition renewal, capacity/subscription policy and finite replay remain authoritative. Read/state/cancel/delete behavior and live control identities are preserved.

ApprovalBridge/Authority must receive the same immutable native application explicitly, since approval-free native callbacks still use ApprovalService prepare_dispatch and recover. Authority renews actor, current policy and exact whole recorded Definition every time, including during recovered historical dispatch. It cannot consult current-only route registration. Source construction changes only private bridge calls/carriers; NativeHostConfig and ApprovalHostConfig fields/literal forms remain unchanged.

Prompt configuration remains the existing current route+task map. Construction/prompt coverage iterates CURRENT definitions only. Park/input prompt lookup must remain explicitly current-whole-Definition guarded before reading prompts; history must never borrow current prompts. Assembly prohibition makes valid historical waiting-for-approval work unsupported in this first increment. Current park, Once/Deny, pending, accepted decisions and TTL behavior remain exact, even when a historical approval-free registration shares the same route/task/effect labels. A recorded unsupported historical approval Definition stays a normal exact-definition refusal, not a converted latest park.

Native input validation presently occurs only for NEW work inside the counted owned producer. Preserve that behavior. Portable validate_input(oldDefinition,input) uses the retained validator exactly, but known-ID/startup recovery and resume do not newly revalidate previously admitted input or reinterpret committed batch input. New v2 work uses the current v2 validator; historical output and callbacks use v1. The design must not claim an HTTP recovery validator call that the source never performs.

## Staging and source boundaries

After current startup final freeze and accepted new design, select only runtime application/registry.rs and validation.rs for production changes if the inherent methods suffice; existing model/control/mod/errors stay protected. Select HTTP route.rs, host.rs, application.rs, recovery.rs, approval.rs, transport.rs and attachment.rs for the common exact selection and private bridge assembly. No worker, lifecycle, supervisor, startup coordinator, cancellation, parser, capabilities, kernel, Store/SQLite schema/driver or dependency change is needed by this candidate. These are proposed exceptions, not current write authorization.

Add only new portable/runtime and independent HTTP history recovery/startup/selection tests/support. Keep old test bodies, manifests/lock/feature graph, current constructors/config literal fields, old wire/storage schemas and all prior public receipts exact. Support may later append a separately counted bounded historical-definition requirement group and narrowly factual documentation, preserving old groups/counts/statuses and no broad RFC/core/client closure. Root must take a fresh baseline after current startup support freeze; the earlier614 protected inventory is a present preservation check, not the next increment's invented final inventory.

Stage a compiling additive API that deliberately ignores history and preserve its source/logs. Independently capture real positive RED, then implement portable exact immutable selection and static assembly restrictions with private TDD. Use the compiled runtime API for independent real SQLite RED before HTTP exact selection GREEN. Root performs complete SPEC and a different nonauthor QUALITY on actual frozen sources; focused positives precede fresh scoped Mac/Linux verification and safe support freeze. No original TypeScript corpus rerun, provider/network installation or live deployment belongs to this slice. Readiness is still bounded startup preparation; actual effect settlement and physical resource retirement remain separate.
